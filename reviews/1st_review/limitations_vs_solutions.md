# How Our Tech Stack Solves the Base Paper's Limitations

| Base Paper Limitation | What It Means | The Tool / Technique | How It Solves It |
| :--- | :--- | :--- | :--- |
| **1. No Intrinsic Knowledge** | The LLM doesn't actually "know" material science deeply. | **FAISS + Sentence-BERT (RAG)** | By converting scientific papers and MOF properties into searchable vectors, the LLM dynamically retrieves and reads relevant facts *before* answering, giving it specialized knowledge on demand. |
| **2. Token Context Limits** | The LLM crashes if you try to feed it massive data tables. | **SQLite + LangChain (Hybrid Retrieval Engine)** | Instead of sending a 12,020-row table to the LLM's prompt, we use SQL to filter the data instantly in the background, only sending the final, small list of matches to the LLM. |
| **3. Reasoning & Logic Errors** | The LLM writes bad code or SQL that fails to run. | **LangChain (Planner + Validator Agent)** | We added an automated "check" step. Before showing results to the user, an agent tests the SQL/Python. If it fails, the agent reads the error and corrects its own code until it works. |
| **4. Restricted Search Space** | They could only search a tiny pool of ~200 frameworks due to memory limits. | **SQLite + FAISS (Multi-stage Retrieval)** | By separating the database layer (SQLite) from the reasoning layer (LLM), we can search the entire database instantly without overwhelming the AI's memory. |
| **5. Narrow Topology Coverage** | They were limited to just 9 specific MOF shapes (topologies). | **Pandas + Full CoRE-MOF Dataset** | By pre-processing the highly diverse CoRE-MOF dataset with Pandas, the system is exposed to all available topologies, breaking the restriction of relying on a small, hardcoded set. |
| **6. Pretrained Model Dependency** | If a property didn't have an existing ML model, their system couldn't predict it. | **FT-Transformer + PyTorch** | We built a custom deep learning architecture that learns the underlying relationships between physical properties directly from the tabular data, allowing us to predict *any* missing property. |
| **7. Un-fine-tuned Models** | General LLMs (like standard ChatGPT) are bad at "reticular chemistry." | **LangChain (Custom Prompt Templates)** | We created highly engineered prompts that inject domain-specific rules (like MOF nomenclature and chemistry logic) into the LLM's instructions, forcing it to act as an expert material scientist. |
| **8. High Compute Overhead** | Running physics simulations (molecular dynamics) takes massive computing power and time. | **FT-Transformer (Surrogate Model) + NSGA-II** | Machine learning predictions take milliseconds. We use the FT-Transformer to estimate properties instantly, and NSGA-II to rapidly find optimal MOFs without running a single heavy simulation. |
| **9. Invalidated Output Quality** | You couldn't trust their recommendations without running expensive tests anyway. | **SHAP (Explainable AI)** | SHAP calculates exactly how much each feature (like pore size) contributed to the prediction. This mathematical proof allows scientists to verify the logic behind a recommendation, building trust. |

**Tip for your presentation:** If your teacher asks about this, just say: *"The base paper relied too heavily on the LLM to do everything, which caused memory and logic bottlenecks. We solved this by treating the LLM just as a reasoning engine, and offloading the heavy lifting to specialized tools like SQLite for data, FAISS for search, and a custom FT-Transformer for predictions."*
